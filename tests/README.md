# Conformance vectors

`vectors.json` is the reference conformance suite. Any verifier claiming conformance — the Go
reference implementation, a future `@gitjob/attest`, or a third-party implementation — must
produce the `expected` result for every case.

```sh
node tests/run-vectors.mjs
# ✓ case 1 (valid) … 4/4 vectors passed
```

The runner drives `examples/tools/verify.mjs` and exits non-zero on the first mismatch, so it
works as a CI gate. `verify-cli.test.mjs` (`node --test tests/verify-cli.test.mjs`) is a
regression test for the verifier's command-line entry point.

## Format

```jsonc
{
  "keyset": [ { "key_id", "public_key" /* base64 ed25519 */, "status", "created_at", "rotated_at" } ],
  "cases":  [ { "receipt": { … }, "expected": "valid" | "tampered" | "unknown_key" | "revoked" } ]
}
```

To verify a case by hand: look up `receipt.key_id` in `keyset` (absent ⇒ `unknown_key`); if that
key is `revoked` as of `receipt.issued_at` ⇒ `revoked`; otherwise canonicalize the receipt with
RFC 8785 JCS omitting `signature`, and check the ed25519 signature over the UTF-8 canonical bytes.

The keys here are ed25519 **public** keys and are non-secret by construction.

## Known divergence — vectors vs. the published schema

These vectors were generated by the reference implementation, whose receipt shape has moved ahead
of the specification text published in this repository:

| | Published `SPEC.md` / `examples/schema/receipt.schema.json` | `vectors.json` |
|---|---|---|
| Version | Draft v0.1 | v0.3 |
| Receipt fields | 7, with `"additionalProperties": false` | 8 — adds `nonce` (and `weight_hash` where present) |

**Consequence, verified rather than assumed:** every vector *verifies* correctly against
`examples/tools/verify.mjs` (4/4), because RFC 8785 canonicalization covers whatever fields are
present and the signature is computed over the same bytes either way. But a vector receipt does
**not validate** against `examples/schema/receipt.schema.json`, because that schema sets
`additionalProperties: false` and does not define `nonce`.

So the signature layer is compatible and the schema layer is not. An implementer who builds to the
published schema and then tests against a real reference receipt will be rejected at validation.

A second divergence, in verification **precedence**: the reference implementation checks
revocation *as of `issued_at`* before the signature (`unknown_key > revoked > tampered > valid`,
as in the hand-verification steps above), while `examples/tools/verify.mjs` and
`examples/README.md` check the signature first and treat `status: "revoked"` as revoked
regardless of `issued_at` (`unknown_key > tampered > revoked > valid`). All four vectors pass
either way, but a tampered receipt under a revoked key, or a receipt issued *before* its key's
revocation, gets a different result from each.

Resolving these is a specification decision, not an editorial one — see the repository `ROADMAP.md`.
